# **Architecture Document — Agent-Driven Fraud Investigation & Institutional Memory Framework**

**Status:** Baseline architecture
**Purpose:** This document is the reference against which implementation decisions should be checked.
**Primary constraint:** Fraud data and derived organizational knowledge must be capable of remaining entirely **on-premise**.

---

## **1\. Product Objective**

Build a cross-platform framework that allows a fraud expert to conduct investigations through AI agents while preserving the complete reasoning and learning generated by those investigations.

The framework should combine heterogeneous inputs such as:

* CSV / Excel
* PDFs and reports
* emails and investigation requests
* Python / VS Code analysis
* notebooks / Colab-style analysis
* existing investigation artifacts
* eventually databases and organizational systems

The AI agent assists with investigation, but the human investigator remains in control of analytical direction and material actions.

The long-term output is not merely an investigation report. It is **institutional memory** containing what happened, what was investigated, what was believed, what was tested, what was rejected, what was learned, and why decisions were made.

---

# **2\. Core Architectural Principles**

### **2.1 On-premise by design**

The complete investigation workflow must be capable of operating without sending organizational data to an external service.

The on-premise boundary includes:

```
Source data
Derived analytical data
Documents
Prompts containing investigation information
LLM inference
Investigation state
Findings
Hypotheses
Decisions
Institutional knowledge
Audit history
```

External LLM APIs or cloud services may eventually be optional deployment choices, but **must not be architectural dependencies**.

### **2.2 The LLM does not own the data**

The agent reasons about the investigation.

It does **not** receive unrestricted direct access to raw organizational data.

Data access is mediated through controlled tools and an analytical execution layer.

### **2.3 Human-controlled investigation**

The agent may:

* understand evidence;
* formulate hypotheses;
* identify unanswered questions;
* propose analyses;
* interpret results;
* recommend subsequent investigation steps.

The human investigator can:

* instruct the agent;
* approve proposed analytical work;
* modify it;
* reject it;
* challenge interpretations;
* introduce hypotheses;
* request alternative analyses;
* approve the final conclusion.

The exact granularity of approval remains a UX/design decision. We should avoid requiring approval for every trivial query while retaining human control over meaningful analytical direction.

### **2.4 Analysis and interpretation are separate**

The analytical engine calculates.

The agent interprets.

For example:

```
Python result:

Device D17
5 accounts
18 events
47-minute activity window
```

is an analytical result.

> "This supports the coordinated-activity hypothesis"

is an agent interpretation.

These must remain distinguishable.

### **2.5 Investigation state, not chat, is the source of truth**

Conversation is an interaction mechanism.

The persistent investigation record is structured state.

A new human or AI investigator should not need to reread a 200-message conversation to reconstruct what happened.

### **2.6 Provenance must be preserved**

Important findings should ultimately be traceable:

```
Knowledge
   ↓
Conclusion / Decision
   ↓
Finding
   ↓
Analysis
   ↓
Human approval/instruction
   ↓
Source evidence
```

# **4\. Component Responsibilities**

## **4.1 Investigation UI**

**Initial implementation candidate:** Streamlit running locally.

The UI is where the investigator interacts with the system.

It should eventually support:

* starting/opening investigations;
* providing instructions;
* viewing agent reasoning at an appropriate summarized level;
* reviewing proposed actions;
* approving/modifying/rejecting actions;
* viewing analytical results;
* inspecting evidence;
* viewing hypotheses/findings;
* reviewing investigation history;
* approving conclusions.

The browser is simply the interface. For V0 it communicates with a server running on the local machine.

**The UI should not contain core investigation logic.**

---

## **4.2 Orchestration Layer**

This is the control plane of the system.

Responsibilities include:

* passing user instructions to the appropriate agent;
* providing agents with relevant investigation state;
* receiving structured agent proposals;
* enforcing approval requirements;
* dispatching approved work to the executor;
* returning results to agents;
* persisting resulting state changes;
* maintaining workflow status.

Crucially:

> **The agent cannot bypass the orchestration layer and independently execute unrestricted analyses.**

---

## **4.3 Investigation Agent**

Initially, this can be a single agent.

Responsibilities:

* understand the business question;
* review available evidence descriptions and relevant evidence;
* formulate competing hypotheses;
* identify gaps;
* propose analytical work;
* interpret returned results;
* update hypotheses;
* generate findings;
* propose subsequent actions;
* eventually propose conclusions and mitigation recommendations.

The agent does **not** own:

* raw data storage;
* unrestricted filesystem/database access;
* ground truth;
* execution permissions;
* final human decisions.

Multiple specialized agents can be introduced later **only if demonstrated to be useful**.

---

# **5\. Local LLM Layer**

Initial inference:

```
Investigation Agent
        │
        ▼
      Ollama
        │
        ▼
    Local Model
```

Ollama provides local model inference.

The architecture should not tightly couple investigation logic to a particular model.

Conceptually:

```
Agent
  ↓
Model interface
  ↓
Local LLM provider
```

This makes later model replacement possible without rewriting the investigation system.

### **Important distinction**

**Local LLM does not mean unrestricted data access.**

Even when Ollama runs on the same machine, data access remains governed.

For V0, our frozen synthetic investigation package provides the initial input.

# **7\. Controlled Analytical Executor**

This is a central security and architectural component.

The agent requests analysis.

The executor performs it.

```
Agent
  │
  │ "Compare account/device relationships"
  ▼
Proposed analytical action
  │
  ▼
Human approval
  │
  ▼
Controlled executor
  │
  ▼
Local data
  │
  ▼
Structured result
  │
  ▼
Agent
```

Initial execution will likely use Python.

Later it could support:

* SQL
* notebooks
* graph analysis
* statistical tests
* approved organizational analytical tools.

### **Data minimization**

Where possible, large raw datasets should remain inside the analytical layer.

Example:

```
10,000,000 transaction rows
            │
            ▼
     Local analysis
            │
            ▼
      23-row result
            │
            ▼
          Agent
```

The LLM receives the information necessary to reason about the result rather than indiscriminately receiving the entire underlying dataset.

# **9\. Evidence, Findings and Hypotheses**

These are different conceptual objects.

### **Evidence**

What exists in the source material.

Example:

```
Account A17
Device D04
Transfer event E108
Timestamp 10:42
```

### **Finding**

Something established through analysis of evidence.

Example:

> Five accounts associated with D04 transferred to two common beneficiaries during a narrow activity window.

### **Hypothesis**

An explanation being evaluated.

Example:

> The accounts may be part of coordinated activity using shared infrastructure.

Therefore:

```
Evidence
   ↓
Analysis
   ↓
Finding
   ↓
Interpretation
   ↓
Hypothesis strengthened / weakened / rejected
```

This separation is mandatory for auditability and institutional memory.

---

# **10\. Human Approval**

Meaningful analytical actions must pass through a human-control mechanism.

Baseline lifecycle:

```
PROPOSED
    │
    ├── REJECTED
    │
    ├── MODIFIED
    │       │
    │       └──→ revised proposal
    │
    └── APPROVED
             │
             ▼
          EXECUTED
             │
             ▼
           RESULT
             │
             ▼
        INTERPRETATION
```

The framework must preserve:

* what the agent proposed;
* why;
* what the human decided;
* any human modification/instruction;
* what actually executed;
* what resulted.

### **V0/V0.5 approval granularity**

For V0 and V0.5, approval applies to exactly one proposed next analytical action, not to the provisional investigation direction or plan. V0.5 retains this boundary while improving the investigator experience; broader long-term approval granularity remains a future design question.

# **11\. Audit & Provenance**

Every material investigation step should eventually be reconstructable.

Example:

```
Agent proposed A014
        ↓
Human modified A014
        ↓
A014-v2 approved
        ↓
Executor accessed:
relationships.csv
events.csv
        ↓
Python operation executed
        ↓
Result R014 generated
        ↓
Agent interpreted R014
        ↓
Finding F008 created
        ↓
Hypothesis H002 strengthened
```

This is both a governance feature and a prerequisite for trustworthy organizational memory.

# **12\. Institutional Knowledge Layer**

The knowledge base is **not simply a vector database containing investigation reports**.

Its purpose is to preserve organizational learning.

Eventually it should support knowledge such as:

> Shared-device behavior was previously investigated as a standalone fraud indicator.

> The hypothesis was weakened because substantial legitimate device sharing was found.

> Device reuse combined with beneficiary convergence and temporal coordination was materially more informative.

And that knowledge should retain lineage back to the investigation that produced it.

Conceptually:

```
Institutional Knowledge
        │
        ├── Pattern
        ├── Context
        ├── Prior hypothesis
        ├── Supporting findings
        ├── Contradicting findings
        ├── Decision
        ├── Outcome
        └── Source investigation
```

The knowledge base must remain within the same on-premise security boundary.

# **13\. Cross-Platform Meaning**

“Cross-platform” does **not** mean we immediately need plugins for every tool.

The architecture should allow the investigation framework eventually to consume or generate work associated with:

```
Excel
VS Code
Python
Notebooks / Colab-like workflows
Email
PDF
Databases
Other analytical systems
```

For V0, integrations are unnecessary.

The architecture should avoid decisions that make them difficult later.

# **14\. V0 Scope**

The first implementation should be deliberately small.

### **Input**

Our frozen deterministic synthetic investigation package:

```
investigator/
evaluator_only/
```

Only `investigator/` is accessible to the investigation system.

`evaluator_only/` exists strictly for external evaluation/testing and **must never enter agent context**.

### **V0 interaction**

```
1. Start local application.

2. Load investigator package.

3. Agent understands available case material.

4. Human gives investigation instruction.

5. Agent proposes a structured analytical action.

6. UI displays:
      purpose
      proposed analysis
      required evidence/data
      expected output

7. Human:
      APPROVES
      MODIFIES
      or DECLINES.

8. Decision is persisted.
```

**No actual analytical execution is required for the first vertical slice.**

The purpose is to validate:

```
Evidence
   ↓
Agent
   ↓
Proposal
   ↓
Human control
   ↓
Persistent investigation state
```

Once this works correctly, we add controlled execution.

# **14.5\. V0.5 Investigator-Ready Investigation Loop**

V0.5 is an approved extension of V0 that preserves the local, governed, no-execution architecture. It adds an investigator-ready navigation and Resume experience, a persisted effective objective, a safe persisted package association, and authoritative persisted lifecycle reconstruction.

V0.5 introduces `InvestigationDirection`: a lightweight, versioned persisted snapshot of ordered textual competing explanations and provisional plan steps. Versions append rather than overwrite and retain minimal provenance. Structured JSON text in SQLite is appropriate for these lists. Direction is not formal Hypothesis, Finding, Evidence, confidence, executable-task, or institutional-knowledge modeling.

After successful initial agent generation, the first direction and first proposal are an all-or-nothing persisted pair: both become authoritative state or neither does. Generation or persistence failure cannot leave a partial initial approach.

The direction is distinct from the one proposed next action. Direction is provisional and never authorizes analysis. Modify retains proposal revision lineage. Decline is authoritative before any replacement generation: the declined proposal and human instruction persist first; a subsequent redirected replacement is independent rather than a revision child, and failed generation cannot roll back the decline.

V0.5 model operation remains synchronous and local. Deployment configuration supplies explicit Ollama endpoint/model and a generous hard processing limit; preflight distinguishes unavailable service or model without silent substitution. The UI presents Agent working during legitimate inference and Attention with explicit recovery/retry after a terminated failure. No background job infrastructure or invisible retry is introduced.

Evaluator isolation remains absolute: evaluator-only material, private truth, and raw structured rows do not enter investigator UI, inventory, prompts, or derived investigator-visible state. Approved actions remain unexecuted; controlled analytical execution remains V1.

# **15\. Planned Evolution**

The current logical sequence is:

### **V0 — Agent/human control loop**

```
Package → Agent → Proposal → Approval → State
```

### **V1 — Controlled execution**

```
Package
   ↓
Agent
   ↓
Proposal
   ↓
Approval
   ↓
Python Executor
   ↓
Result
   ↓
Agent interpretation
```

### **V2 — Investigation state**

Persist:

```
hypotheses
findings
questions
actions
decisions
results
```

### **V3 — Complete investigation**

Allow iterative investigation through multiple analytical actions.

### **V4 — Institutional memory**

Extract reusable knowledge while preserving provenance.

### **Later**

Only as justified by actual use:

* multiple agents;
* graph visualization;
* Excel integration;
* database connections;
* VS Code integration;
* notebook execution;
* richer document ingestion;
* organizational knowledge retrieval;
* multi-user deployment;
* enterprise authentication/authorization.

# **16\. What We Explicitly Should Not Build Yet**

To protect scope, the following are **not current requirements**:

* custom React frontend;
* cloud platform;
* SaaS deployment;
* multi-agent hierarchy;
* autonomous unrestricted investigation;
* sophisticated graph UI;
* production vector database;
* enterprise SSO;
* real-time fraud detection;
* transaction-scoring engine;
* fraud model;
* synthetic-data generator expansion;
* integrations with every analytical platform;
* large-scale data infrastructure.

The framework is an **investigation and organizational-learning system**, not a fraud-detection platform.

---

# **17\. Architectural Invariants**

These are the rules I would use when reviewing future implementation.

### **INV-01 — Locality**

Core investigation must work without sending investigation data outside the controlled environment.

### **INV-02 — Governed data access**

Agents do not receive unrestricted raw-data access.

### **INV-03 — Human authority**

Meaningful analytical actions cannot bypass the defined human-control mechanism.

### **INV-04 — Grounding**

Findings must ultimately be traceable to evidence or analytical results.

### **INV-05 — Separation of calculation and interpretation**

Analytical execution does not silently make fraud conclusions.

### **INV-06 — Persistent structured state**

Material investigation knowledge cannot exist only in conversation history.

### **INV-07 — Provenance**

Actions, decisions, results and resulting findings retain lineage.

### **INV-08 — Knowledge lineage**

Institutional knowledge retains a connection to the investigations and evidence from which it was learned.

### **INV-09 — Model independence**

Core business logic is not tied to a specific LLM.

### **INV-10 — Evaluator isolation**

Synthetic evaluator ground truth is never accessible to the investigation agent.

### **INV-11 — Incremental scope**

New infrastructure is introduced only when an actual framework requirement demonstrates the need.

## **Definition of success**

The architecture is working as intended when a fraud expert can give an AI agent an investigation objective, allow it to formulate and propose analytical work, retain authority over what is executed, have analysis performed against locally controlled data, inspect the evidence behind the agent's conclusions, and preserve the resulting reasoning and decisions as reusable organizational knowledge—**without requiring sensitive fraud data or knowledge to leave the organization's environment**.
